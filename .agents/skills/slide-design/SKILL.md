# slide-design - choose a direction from real covers, not from adjectives

Users who cannot say what style they want are the norm; letting them pick from three real covers works far better than asking "what style do you like?".

## Prerequisite

`pnpm story:check decks/<id>/story.md --require-confirmed` has to pass. If the story is not confirmed yet, go back to slide-story.

If the user has already named a theme, or `decks/<id>/design.json` exists and the user has not asked for a change, skip to step 6, confirm the theme id and move to slide-build.

## Steps

### 1. Read the tone of the story

From the audience, occasion and core message in story.md, judge the tone: formal or relaxed, internal or external, persuading or teaching. That decides where the three directions land.

### 2. Pick three candidates from the template library

Do not invent directions (home-made themes have always lost to ported mature templates; four rounds of pitches were rejected). The source is [beautiful-html-templates](https://github.com/zarazhangrui/beautiful-html-templates) (MIT, 34 sets; keep a local clone, path of your choice): read its `index.json`, match the story's tone against `mood` / `tone` / `formality` / `density` and choose three sets that are **genuinely different from each other** (one safe, one bold, one unexpected), then put their `screenshots/` on a one-page gallery for the user (example: `artifacts/design/<deck-id>/template-gallery.html`). Theme packs already ported (the themes `pnpm layouts` lists) can be candidates straight away; `docs/gallery/index.html` (regenerated by `pnpm theme:gallery`) has a page for each of them with the layouts it ships, ready to put in front of the user.

### 3. Port the candidates into theme packs

One template = one theme pack: `themes/<slug>/theme.{json,css}` owns the look, `themes/<slug>/layouts/<id>/` holds the pack's own layouts (a layout with the same id overrides the generic one). For the pitch, port only the cover (`layouts/cover/`); once the user has chosen, port that set's remaining layouts. The method and the conversion rules are under "Porting a theme pack" in [references/design-directions.md](references/design-directions.md). Then:

```bash
pnpm theme:lint
```

Continue only at zero errors. A theme may only set appearance; a geometry property fails the lint, and the pack's own layouts are checked with it.

### 4. Render the previews

```bash
pnpm design:preview decks/<id>/story.md --theme <theme-id>
```

Run it once per direction; the output is `artifacts/design/<id>/<theme-id>.png` (with the `.html` beside it). The layout defaults to `cover` and the pack's own cover is found first; `--layout <id>` previews another. The preview uses the real content of the story's first slide, so no process text ever appears on it; do not hand-make preview pages. Putting the three PNGs next to the original template screenshots on one page (example: `artifacts/design/<id>/round4.html`) makes the comparison easier.

### 5. Let the user choose

In the message, list the paths of the three PNGs, each with one sentence of description and its theme id; the direction names and theme ids appear only in the message. Ask which one the user picks, or what they would like to mix (e.g. A's typeface with B's colours). For a mix, create a fourth theme and preview again.

### 6. Record the choice

```bash
pnpm design:set decks/<id>/story.md --theme <theme-id> [--direction "<the direction's name>"]
```

It checks that the theme pack can be found from the deck folder and writes `decks/<id>/design.json` (`theme`, `direction`, `chosenAt`; the schema is `schemas/design.schema.json`). Do not write the file by hand. `deck:scaffold` takes the theme from it, so the build needs no `--theme`; a deck that is already built moves with `pnpm deck:retheme decks/<id>/deck.json --theme <theme-id>`.

The themes not chosen can stay for later; delete them only when the user asks. Then move to slide-build.

## What this skill does not do

- It does not decide for the user, and it never offers a single direction.
- It does not offer three directions that differ only in colour; it does not build themes from scratch, and it does not mix the layouts of two templates.
- It puts no text from the user's requirements ("bold", "internal sharing" and the like) and no theme name into a preview or a theme.
- It avoids gradients, drop shadows, Inter / Roboto and white-with-purple-gradient looks that smell of defaults (see the references).
